# Stakeholder Analysis

The Study Planner system involves five stakeholder groups whose needs, constraints, and objectives directly inform system requirements.

---

## 1. Students (Primary Users)

Students are the primary stakeholders and the intended users of all system features.

**Needs:**
- Import module and assessment data from a structured file
- Define and manage study tasks, dependencies, and milestones
- Log study activities and track measurable progress
- View progress on a dashboard and Gantt chart

**Influence on requirements:**
- Drive usability design, system responsiveness, and clarity of visual feedback
- Require intuitive error messages that explain corrective actions
- Need persistent data that survives across sessions

---

## 2. School of Computing Sciences (Client)

The School of Computing Sciences acts as the commissioning body. The Study Planner is initially intended for use within the School, with potential expansion to other schools.

**Objectives:**
- Support structured academic planning across all year groups
- Encourage proactive study behaviour and reduce last-minute submissions
- Explore potential integration with institutional systems (UEA Hub)

**Influence on requirements:**
- Defines the expected data file format exported by the Hub
- Requires the system to be maintainable and scalable beyond a single school
- Sets expectations around data validation and audit-readiness

---

## 3. Academic Staff and Module Organisers (Indirect)

Module organisers define assessment structures and may change deadlines throughout the semester.

**Influence on requirements:**
- System must support deadline updates without loss of existing student data
- Assessment information must be accurately represented in the system
- The data model must be flexible enough to accommodate diverse assessment types (coursework, exams, demonstrations)

---

## 4. University IT Services / Hub System (External Technical)

The Study Planner relies on module and deadline data generated by the UEA Hub system on a per-student basis.

**Constraints introduced:**
- A defined and validated file format (`.csv` or `.json`) must be supported
- Uploaded data must be verified before persistence
- The architecture must remain open to future API-based integration

---

## 5. Future Schools within UEA (Long-term)

Although initially developed for Computing Sciences, the system may later be adopted by other UEA schools.

**Influence on design:**
- The data model must support flexible module structures
- Assessment modelling should be generalised, not tied to computing-specific types
- The system architecture must support multi-school scalability

---

## Stakeholder Summary Table

| Stakeholder | Type | Primary Concern | Influence on System |
|---|---|---|---|
| Students | Primary User | Usability, progress visibility | Core feature set, UI design |
| School of Computing Sciences | Client | Academic planning, scalability | Data format, institutional requirements |
| Academic Staff | Indirect | Accurate assessment representation | Deadline updates, data flexibility |
| University IT / Hub | External Technical | Data format, future API | File format specification, validation |
| Other UEA Schools | Future | Scalability | Flexible data model, generalised design |
